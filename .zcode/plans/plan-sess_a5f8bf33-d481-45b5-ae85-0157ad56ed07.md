## 目標（方案 M：精簡 + 翻頁）
把 `getMyBugs`（及 stdio 入口 `browseBugs`）從「固定返回含大段 HTML steps 的全量對象」（實測 20 條 ~228KB ≫ 工具輸出上限 ~50KB，會被 client 截斷 `[Tool output truncated...]`）改為：**永遠精簡（5 字段）+ offset 翻頁**。

砍掉前五版的 `includeSteps` 開關與 server 降級邏輯——審查確認那是為邊緣場景背負的高複雜度。看 steps 用已有的 `getBugDetail`；看全貌/統計用已有的 `getBugStats`。`getMyBugs` 帶 steps 本是設計缺口，直接對齊其他工具的精簡風格即可。

## 為什麼是 M 而非 S/F
- **vs S（最簡，僅精簡）**：M 多了 offset，解決「精簡列表條數多（如 200+ 條 assigntome）時單次讀不全」的真實需求。
- **vs F（完整，含開關+降級）**：M 砍掉 budget 測量、降級、notice 欄位等 80% 複雜度。精簡數據天然不超限（20 條 ≈ 2KB ≪ 50KB），從根源消除截斷，無需降級兜底。

## 已審查的技術風險（無阻斷）
- **offset 在客戶端過濾情境（assigntome+moduleId）的穩定性**：server 數據變動會導致過濾後序列漂移、翻頁可能跳/重。但這是所有客戶端過濾分頁的通病，且 `getBugStats` 已接受此情境 total 不精確（註釋 443 行），屬已知禪道 server 限制。會在 README 如實標註「此情境下翻頁可能不穩定」。
- **hasMore 準確性**：一般情境用精確 total；客戶端過濾情境用 reachedEnd 信號（比猜總數可靠）。

## 不做的事
- 不加 includeSteps 開關、不加 server 降級、不加 budget 測量、不加截斷引導（精簡後不需要）。
- 不動 getBugDetail/getMyBug/getBugStats/getNextBug。
- 精簡嚴格 5 字段，與 getBugStats/getNextBug 完全對齊。
